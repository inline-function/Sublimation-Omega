## 2 前端模块组成（本期交付边界）

- 包根 `sublimation.frontend`（旧包名 `sugared.functor` 退役）。
- 子包按管线分层：`lexer` → `ast` → `parser` → `hir` → `semantic`，横切 `diag`（诊断），出口 `json`（HIR→JSON）与对外的编译入口。
- 对外契约：以**单源文件**为处理单位（S-1 §0）；提供「源代码 → HIR → JSON 文件」的一次编译 API 与最小调用入口。
- 语义分析在 HIR 构造过程中完成（S-1 §3）：名称解析、类型推导、证明检查在 `semantic` 内闭合，不得前置到 AST 层（AST 保持零语义，S-1 §2）。

## 3 依赖规则（硬规则）

1. 模块依赖方向严格沿管线前进，禁止回望与跨层引用（S-1 层间总契约 1）。
2. 包级依赖方向：`parser → lexer`、`semantic → ast/parser`、`json → hir`；`diag` 为横切模块，**零依赖、可被任层依赖**（ADR-4 裁定：diag 宿 Severity/SourcePos/SourceRange/NodeId/Diag/DiagBag，lexer/ast/hir 等单向依赖之）。禁止反向。HIR 是管线终点，任何包不得依赖 `json` 之外的下游（D-8）。
3. `:frontend` 零第三方运行时依赖（沿用旧实现传统，见《形式化文法》§0）；JSON 产出手写发射器（提案，见 P-6）。
4. 构建约定统一：Kotlin 2.1.20、JVM 17 toolchain、JUnit Platform、测试工作目录 rootDir（对齐旧工程构建配置）。
5. 非本期模块（`:backend-js` / `:cli`）在 `settings.gradle.kts` 中暂不 include；待相应管线阶段启动时追加，且必须先修订本文件留痕。`:lowering` 永不建立（D-8）。

## 4 前端包结构（提案）

```
sublimation.frontend
├─ lexer      词法单元流（Token、Lexer；契约 S-1 §1）
├─ ast        抽象语法树（零语义节点；契约 S-1 §2）
├─ parser     语法分析（递归下降；规则《形式化文法》S 层 / D 层）
├─ hir        高级语义树节点（命题与证明的唯一住所，S-1 §3）
├─ semantic   语义分析：降级 AST→HIR、名称解析、类型推导、证明检查
├─ diag       诊断模型（携带源位置；S-1 层间总契约 2）
├─ json       HIR → JSON 产物发射
└─ 编译入口    单文件 → HIR → JSON
```
