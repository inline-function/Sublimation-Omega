# 标准库规划（讨论稿）

> 状态：**讨论稿，待用户裁决**（§8 五条）。队长 2026-11-08 15:4x 起草。
> 缘起：用户提出「`axiom ∀n. n : Nat → n >= 0` 应作为标准库的一部分放在公理库中」，并要求开始讨论标准库的构成。

## 1 先把现状说清楚

今天的 `Nat ⇒ n >= 0` 是 **t65 在编译器里注入的**（`provenance=type`），不是公理，也不在任何库里。这有三个问题：

| 问题 | 后果 |
|---|---|
| **不可读** | 用户无法知道编译器"免费"给了哪些事实 |
| **不可审计** | 健全性论证时无法列举「我们默默假设了什么」 |
| **不可移植** | 换实现就得重新发明这套事实，且可能与旧实现不一致 |

用户的方向是对的：**这些应当写成公理，成为语言定义的一部分**。

## 2 三层结构（提议）

```
内核层 kernel      类型（Nat/Int/Rat/Bool/Str/Null/Nothing/Any/Range/Real）与原生操作
                   + 内核公理（可列举、只读、随编译器版本）
核心库 core        Option/Result/List/Map/Set/Channel/Tuple —— 类型与函数
公理库 axioms      关于核心库的命题（长度、插入、外延性…）
```

**现状**：内核层与核心库**都写在 Kotlin 里**（`PreludeDecls.kt` 虚拟声明 + `builtinSig` 函数表）；公理库**不存在**。

## 3 公理库：首批清单（提议）【2026-11-14 对账标注（t156/B3）：A1–A3 + L1–L4 已落 stdlib/axioms（@axiom 无体 fun 形）;M/S/T/G 与 L5–L7、E1–E3、induction 仍暂缓（t91 裁决 6 延续）】

标记含义：**【公理】**必须作公理（证明需归纳/未实现）；**【可证】**理论可证但当前不可（留待归纳法落地后转为定理）；**【内置】**已在实现里，公理仅作规格声明。 【2026-11-09 对账标注（t91）】归纳法暂缓待讨论（裁决 6）。

### 3.1 数值（与用户裁决直接相关）

| # | 公理 | 类 | 说明 |
|---|---|---|---|
| A1 | `∀n: Nat. n >= 0` | 内置 | **用户点名的那条** |
| A2 | `∀n: Nat. ∀m: Nat. n + m >= n` | 内置 | 无界 ⇒ 成立 |
| A3 | `∀n: Nat. ∀m: Nat. n - m >= 0 ⟺ n >= m` | 内置 | 减法收窄的根据（ST-10.2）|
| A4 | `∀n: Nat. ∀m: Int. n <= m ⟹ n - m <= 0` 之类的跨塔律 | 可证 | 视是否需要 |
| A5 | `Int`/`Rat` 无界无符号约束 | — | 不给公理（无事实可给）|

## 4 关键缺口一：命题里无法表达「`n` 是 `Nat`」

用户写的 `∀n. n : Nat → n >= 0` 里，`n : Nat` 是**类型判定**。而：

| 事实 | 证据 |
|---|---|
| 量词是**无类型**的 | `S-40 【量词表达式】 ::= ("∀"|"∃"|"∃!"|别名) 【量词名】+ "." 【表达式】` —— 没有 `: 类型` 位 |
| 样本用法 | `axiom forall n. tagged<n>`（`上下文弥散.subl:32`）|
| 类型判定 `(e : T)` | **ADR-13 §三 明确推迟**，实现零处 |

**所以用户那条公理现在根本写不出来。** 两条路：

| 方案 | 形态 | 代价 |
|---|---|---|
| **A. 有类型量词** | `∀n: Nat. n >= 0` | 词法/文法小改；语义 = 「n 取值范围限于 Nat」；需定义「量词绑定类型的公理自动可见」 |
| **B. 类型判定进命题** | `∀n. (n : Nat) → n >= 0` | 即 ADR-13 推迟项；更通用，但工作量大 |

**队长建议 A**：标准库需要的是「按类型限定个体」，不是通用类型判定；A 的语义边界清楚（量词域 = 该类型的值），可先落地；B 留给 P-12 第 ③ 级。

## 5 关键缺口二：标准库用什么语言写

现状：核心库是 **Kotlin 里的虚拟声明**（`PreludeDecls.kt` + `builtinSig`）。后果：

- 语言**没有吃过自己的狗粮**——最核心的容器不是用本语言写的；
- 用户看不到 `List` 的定义（只能在 e2e 样本里看到仿写版 `core/collection/list.subl`）；
- 公理库若用 `.subl` 写，就得先有**模块系统**（当前 `list.subl`、`主.subl` 两条红都是它）。

**分阶段建议**：

| 阶段 | 内容 | 前置 |
|---|---|---|
| S1 | 保持 Kotlin 虚拟声明（今天这样）；公理库先用 `.subl` 单文件形式随程序编译 | 有类型量词（§4-A）|
| S2 | 模块系统落地 ⇒ 核心库迁到 `.subl` 源码，内核只留「编译器必须知道的东西」（字面量类型等）| 模块系统 |
| S3 | 用本语言写的核心库 + 公理库，形成可自举的规格 | S2 |

## 6 类型事实与公理库的关系（**spec vs 优化**）

t65 的注入与 A1 公理**做的是同一件事**。两者不应各说各话，建议：

| 角色 | 归属 |
|---|---|
| **规格（of record）** | 公理库里的 A1 |
| **实现（快路径）** | 编译器注入（t65），按类型位直接产生事实，不实例化公理 |
| **一致性测试** | 断言「编译器注入的每条事实，都能由公理库实例化得到」——防止快路径与规格漂移 |

这条测试很便宜（比公理实例化便宜得多），但能抓住最危险的一类 bug：**快路径悄悄多给了公理没允许的事实**。

## 7 信任、审计与版本

| 类别 | 计入 `trustedBase`？ | 可列举？ |
|---|---|---|
| **内核公理**（A1–A3、L1、M1…）| **否**——它们是语言定义的一部分 | **是**：`--print-kernel-axioms` |
| 编译器类型事实（t65 注入）| 否（来源 `type`）| 是（`--print-type-facts`，调试用）|
| **用户公理** | **是** | 是（`trustedBase`）|

**为什么内核公理不计入 `trustedBase`**：`--no-trust` 的语义是「本次通过不依赖**用户**未证断言」。若把内核公理也算进去，任何程序都无法通过 `--no-trust`，该模式就废了。

**但必须可列举**：否则「健全性以用户公理为条件」这句话就是半真——用户会以为内核没有假设。**内核假设必须公开在文档里**（本文 §3 就是它的第一版）。

版本：公理库版本号与语言版本绑定；公理**只增不改**（改 = 破坏向后兼容），删改须走 ADR。
