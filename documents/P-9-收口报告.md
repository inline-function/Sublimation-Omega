## 3. 八条裁决独立复核表

复核方法：对每条裁决**独立编写探针**（文件名 r{裁决}{子项}，置于 frontend/build/tmp/p9/），以 CLI check 子命令（java -cp 前端 jar + kotlin-stdlib）实测，不运行他人测试。判定口径：裁决子项全部成立=通过；有一子项不成立=不成立；裁决字面与语言形态有口径差但语义落点成立=带口径差通过。

### 裁决 1：删 enum —— 通过

- 裁决原文：「enum E { A } 须报 E-ENUM-REMOVED；struct A + type E = A | B 须通过」
- 实测：r1a「enum E { A }」→ E-ENUM-REMOVED（1:1，附迁移指引：struct + 联合别名）✓；r1b「struct A / struct B / type E = A | B」→ 零错通过 ✓
- 判定：**通过**

### 裁决 2：删 def —— 通过（字面形态口径差，已落点）

- 裁决原文：「def 报 E-DEF-REMOVED；命题位未定义名不报未定义；axiom Even(4) ↔ ∃k . 4 = 2k 须通过」
- 实测：r2a「def f(): Nat = 0」→ E-DEF-REMOVED ✓；r2c「axiom Foo(Bar)」→ 零错（命题位未定义名 Bar 不报）✓；裁决原文字面的「4 = 2k」（隐含乘法）不通——E-SYNTAX「期望)，实际'k'」；按 ADR-28:15 自身写法「axiom Even(4) ↔ ∃k . (4 = 2 * k)」→ 零错通过（工程/脚本两模式均过）✓
- 判定：**通过**（歧义已指出：裁决示例用了语言不支持的隐含乘法写法「2k」；以显式 2 * k 形态落点，与 ADR-28 一致）

### 裁决 3：删 val —— 带口径差通过（附诊断质量发现）

- 裁决原文：「val 报 E-VAL-REMOVED；顶层 var 在脚本模式允许、在模块模式报错；var 不得在 trait 体内」
- 实测：r3a3「class T { val x: Nat }」→ E-VAL-REMOVED ✓（Parser.kt:703 的废除指引）；r3b「var x = 1」工程模式 → 报错（E-SYNTAX：顶层只能写声明）✓；r3c「var x = 1」脚本模式 → 零错通过（附 D-TYPE-INFERRED）✓；r3d「class T { var x: Nat }」→ 报错（E-SYNTAX：类型类体内禁止字段声明）✓
- **口径差/发现**：语句位的 val 不落 E-VAL-REMOVED——工程模式顶层「val x = 1」落通用 E-SYNTAX；脚本模式与函数体内（r3a2/r3a4）val 被解析为标识符落 E-UNBOUND-NAME ×2（无废除指引）。即 val 在所有位置都被拒绝，但裁决点名的专用码只在 class 体内触发。
- 判定：**带口径差通过**；行为层面 val 已彻底废除 ✓，诊断质量层面建议补语句位指引（§6 待办 4）

### 裁决 7：归纳类型 —— 不通过（判据/裁决口径冲突，裸自引用联合被误报）

- 裁决原文：「type Peano = Zero | Succ[Peano] 通过且落 D-INDUCTIVE-TYPE（SUPPLEMENT 级）；type A = A 报 E-CYCLE；type A = A | B 视为归纳通过」
- 实测：r7a2（结构体先声明后「type Peano = Zero | Succ[Peano]」）→ 零错通过 + **D-INDUCTIVE-TYPE（SUPPLEMENT 级）**✓（附注：裁决字面的裸形态——Zero/Succ 未声明——落 E-UNBOUND-NAME ×2，属合理：构造子须作为 struct 存在，与 list.subl 的既有写法一致；D-INDUCTIVE-TYPE 仍正确落盘）；r7b「type A = A」→ **E-CYCLE**（右值成员全部引用自身，无基态）✓；r7c2「struct B / type A = A | B」→ **E-DUP-UNION-MEMBER：联合类型 A 的成员 B 重复声明（联合成员不得重复）** + 附 D-INDUCTIVE-TYPE，退出码 1 → **未通过**；交叉验证 r7d「type A = B | A」（自引用在后）→ 同样误报 E-DUP-UNION-MEMBER；r7e「type A = A | A」（真重复）→ 正确落 E-DUP-UNION-MEMBER + E-CYCLE
- 分析：判重逻辑把「联合别名自身的裸自引用成员」与「其它成员」误判为重复（文案指向 B，但 B 全文仅出现一次）。构造子应用形态的自引用（Succ[Peano]）不受影响。裁决明确要求「type A = A | B 视为归纳通过」，当前实现相悖。
- 判定：**不通过**（3 个子项中 2 项通过；「A | B 裸自引用视为归纳通过」子项不成立——缺陷或判据需修订，详见 §6 待办 3）

### 裁决 8：遮蔽 —— 不通过（1 个类型检查缺陷）

- 裁决原文：「顶层同名自由函数报 E-DUP-DECL；同域同名扩展函数报 E-DUP-EXT；局部同名后遮蔽前并落 H-SHADOW（HINT 级）；局部扩展函数可用；内层 fun f(a: Str) 遮蔽外层 fun f(a: Nat) 后 f(0) 非法」
- 实测：r8a（两个同名自由函数）→ **E-DUP-DECL** ✓；r8b（同接收者头 Nat 两个 g，参数表不同）→ **E-DUP-EXT** ✓（两处均报，文案引 TS-13、V1 禁重载）；r8c（块内 var 遮蔽 / 局部函数遮蔽）→ **H-SHADOW，提示（HINT）级** ✓（两种形态均落，且语义正确：内层解析不回退）；r8d（局部扩展函数 fun Nat.loc() + z.loc() 调用）→ 零错可用 ✓
- **缺陷**：r8e（内层 fun f(a: Str) 遮蔽外层 fun f(a: Nat) 后 f(0)）→ **零错通过，裁决要求非法却合法** ✗。分离探针定位根因：r8f（**无外层函数**，仅局部 fun f(a: Str)，调用 f(0) 即 Nat 实参传 Str 形参）→ 同样零错放行；对照 r8h（全局 fun f(a: Str) 被 f(0) 调用）→ E-TYPE-MISMATCH。结论：**局部函数的调用点不做实参类型检查**（全局函数做），由此裁决末条不成立（H-SHADOW 虽然声称「不回退」，但调用 arg 类型未按可见的局部函数校验，f(0) 既未按内层 Str 报错、也未按外层 Nat 解析报错——直接静默放行）。
