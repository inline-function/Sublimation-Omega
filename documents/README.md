# documents/ — 文档总纲

Sublimation 的文档体系。五类文档，各司其职，互不越界。

## 目录角色

| 目录 | 角色 | 读者 | 回答的问题 |
| --- | --- | --- | --- |
| `idea documents/` | 理念文档 | 未来的维护者 | **为什么**这样设计？ |
| `boring documents/` | 形式化文档 | 编译器作者 | 语言**精确地**是什么？ |
| `root documents/` | 根文档 | 语言使用者 | 这门语言**怎么用**？ |
| `wiki/` | 维基 | 所有人 | X 是什么？怎么写？有什么坑？ |
| `log/` | 开发日志 | 未来的我们 | **当时**发生了什么？ |

## 权威等级

当不同文档互相矛盾时，按以下顺序裁决：

**boring documents ＞ root documents ＞ wiki**

- 形式化文档是编译器行为的**最终依据**
- 根文档与维基是它面向人的翻译
- 理念文档不参与裁决——它只记录动机，不定义行为

## 写作规范

### boring documents/（形式化卷）

- 形式化文法：每条产生式带编号（如 `G-λ-1`）
- 形式化语义：每条语义规则带编号（如 `S-IMMUT-1`）
- 诊断码与测试用例应能追溯到规则编号
- 禁止"显然""易得"——一切结论可追溯

### root documents/（根文档）

- 面向使用者的主题手册，由浅入深
- 可以讲故事、给直觉，但每条技术断言应能在 boring documents 找到对应规则

### wiki/（维基）

- 一页一概念，固定四节：**语法 / 语义 / 示例 / 陷阱**
- 语义节必须引用对应的 boring documents 规则编号
- 条目间互相链接

### idea documents/（理念文档）

- 每个重大设计决策一份记录，ADR 风格：**背景 / 候选方案 / 决策 / 后果**
- 编号连续，追加而不覆盖
- 决策被推翻时保留原文，标注"已被 ADR-x 取代"

### log/（开发日志）

- 编年体，一天一文件（`YYYY-MM-DD.md`）
- 记录过程：做了什么、卡在哪、改了什么主意
- 不追求可读性，追求可追溯

## 信息流

```
理念文档 ──动机──> 形式化文档 ──翻译──> 根文档
                    │                    │
                    └────── 维基 ────────┘
                     （速查：一页一概念）

开发日志独立记录一切过程
```

理念文档立项 → 形式化文档定义 → 根文档教学 → 维基索引。
反方向：读者在维基/根文档发现的疑问，回流为新的理念文档选题。
