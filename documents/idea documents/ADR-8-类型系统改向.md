## 一、用户口述原文（2026-11-04，不可改写）

> 我们一开始的类型系统是类似于 Rust/Haskell 那派的类型类与特质，我打算改成类似 Golang 那派的，
> 原先是 class struct impl 三要素，现在我打算把 impl 去掉。class 依旧声明一组函数规范，即类型类，
> struct 也一样，函数名前面可以加上其扩展类型，那么此函数就是那个类型的扩展函数（和 kt 差不多），
> 比方说这样 fun Nat.f() 对自然数扩展一个 f 函数，如果一个类型被扩展的函数满足某个类型类，
> 则认为这个类型是那个类型类的子类型。

---

## 二、决策

**D1 废除 impl**：类型系统由三要素降为二要素（class + 类型声明）。impl 出现即报 `E-IMPL-REMOVED`，不设兼容期。

**D2 类型类用 class 表达**：class 体只含函数规范（无实现体、无字段），`Self` 为隐式占位类型，可带实参（`Self[A]`）以表达对类型构造器的要求。

**D3 实现用扩展函数**：`fun Receiver.name[T](...): R`。接收者在函数体内以 `self` 绑定。三种调用形态（方法糖 / 直接调用 / 类型限定）语义等价。

**D4 满足是结构性的**：T 满足 C ⇔ C 每条规范都有以 T 为接收者的扩展函数在 Self:=T 后签名一致。判定在**使用期**做（可前向引用），诊断必须列缺失规范清单。

**D5 V1 不做字典传递**：约束只做编译期满足检查，不做运行时分派。理由见 ADR 四·1。

**D6 六个待决问题的裁决**：Q1 使用期判定；Q2 重复报 `E-DUP-EXT`、直接调用自由函数优先；Q3 `by` 委托 V1 废除；Q4 类型类继承保留；Q5 `for` 关键字释放；Q6 不设兼容期。详见类型系统卷 §8。

## 三、后果

### 3.1 必须改动（全链路）

| 层 | 改动 |
| --- | --- |
| 词法 | `impl` 由硬关键字降为「保留字（报错用）」；`for` 释放；扩展函数名形态 `类型.名字` 需词法支持 |
| 语法 | 删除 ImplDecl 全部产生式；新增扩展函数产生式（函数名前接接收者类型）；class 体只允许规范/常量/继承 |
| AST | 删 `ImplDecl`；`FunDecl` 增接收者字段 |
| HIR | 删 `HirImplDecl`；`HirFunDecl` 增 `receiver`；新增 `HirSelfType`；JSON schema 升 `hir@v2` |
| 语义 | 扩展函数登记桶、方法糖改查扩展桶、结构化满足检查器、约束检查、六个新诊断码 |
| 样本 | 所有含 impl 的样本手工迁移（`impl T for U {f}` → `fun U.f()`）；`by` 委托样本改写 |
| 测试 | 现有 327 个测试中含 impl 的用例全部重写；新增满足判定与约束检查用例 |

> **分阶段实施注记（P-8/A，t27，2026-11-06）**：上表「AST」「HIR」两行的**增量部分**先行落盘——
> `FunDecl.receiver: Type? = null`（末位以兼容既有位置构造点）、`HirFunDecl.receiver: HirType? = null`、
> 新增类型节点 `HirSelfType`；JSON 发射按 TS-31（自由函数**省略** receiver、扩展函数**必现**且嵌套实参原样保留、
> Self 固定 `{"k": "self"}`）。schema 版本**本阶段仍 v1**——升 v2 与 `ImplDecl`/`HirImplDecl` 的删除统一在
> C 阶段（t29）落，故 A 阶段 ImplDecl/HirImplDecl 原样保留（与上表所列删改的时序差，非决策变更）。
> 树可编译、既有行为不变（:frontend:test --rerun-tasks 331 tests 0 failures）。
> 两处穷尽 when 的被动补支：`TypeInfer.render` 的 `is HirSelfType -> "Self"` 与 `HirTest.typeName` 的
> `is HirSelfType -> "self"`（新增 sealed 子类型的编译必需，语义层填充在 t30）。

### 3.2 正面后果

1. **与用户方向一致**：语言更接近 Go 的隐式接口满足，声明更短。
2. **HIR 更瘦**：impl 这层中介结构消失，函数与其接收者直接关联。
3. **前向引用天然合法**：满足判定在使用期，扩展函数可后置声明。

### 3.3 负面后果与缓解

1. **失去显式分派点**：V1 无字典传递，因此「一个泛型函数对多种类型工作」只能靠**编译期特化**（每次调用点解析到具体扩展函数）。缓解：V1 样本以具体类型为主；泛型 + 类型类的组合留待后继卷。
2. **迁移成本**：7 个样本 + 含 impl 的测试需改写。缓解：一次性完成，不留兼容层（避免长期双轨）。
3. **`Self` 与接收者两个概念易混**：已用 TS-25/26/27 三条划界，并在诊断上区分 `E-SELF-OUTSIDE-CLASS`。

## 四、备选方案与取舍

1. **保留运行时分派（字典传递）**——否决。HIR 需携带字典构造与传递链，复杂度高；且用户方向里「满足即子类型」本身是类型关系，不是分派机制。留待后继卷。
2. **保留 impl 作为语法糖**——否决。双轨会让语义层长期维护两套登记与解析路径，与「旧工程重构」的目标冲突。
3. **class 规范用 Haskell 形态 `class Functor[F[_]]`**——否决。`F[_]` 的 kind 标注在新语法里无先例，且与「Self 占位」相比表达力等价而解析更重。选 `Self`。
4. **直接调用时按「更具体者胜」打分**——否决。不可预测，同一源码在不同实现下可能解析不同。选「自由函数优先」的确定性规则。
