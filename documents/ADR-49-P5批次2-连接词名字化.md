# ADR-49 P5 批次 2：`∧ ∨ → ↔` 名字材料化（词法放开 + 路由回落 + 产物逐字不变）

- 日期：2026-11-09
- 任务：t74（原派 semantics，因**配额耗尽**中断，由队长接管完成）
- 前序：t72（qa 影响面测绘）、t73（批次 1 修路：命题位 `propCtors` 分派）
- 裁决链：用户 R1（粘连即整体）、R3（`f(a,b)` 表达式 vs `f<a,b>` 命题）、N1（`¬p` 是标识符）、A1–A3（中缀一律左结合，无优先级）

## 一 决策：`∧ ∨ → ↔` 进【名字材料】

| 项 | 改动 |
|---|---|
| `logicalSingletons` | `∀ ∃ ∧ ∨ → ↔ ⊤ ⊥` ⇒ **`∀ ∃ ⊤ ⊥`** |
| `nameMaterialSingletons` | `¬` ⇒ **`¬ ∧ ∨ → ↔`** |
| 单字符分派 | 删除 `∧→LAND` / `∨→LOR` / `→→IMPLIES` / `↔→EQUIV` 四行 |

**为何必须删这四行**：名字材料通道（`readIdent`）在单字符分派**之前**命中，四行从此不可达——留着即死代码（S-4 禁止）。
`Kind.LAND/LOR` 仍由 ASCII 别名 `&&` / `||` 产出（词法归一文本仍为 `∧` / `∨`）；`IMPLIES/EQUIV` 同 `LNOT` 口径仅留枚举量。 【2026-11-09 对账标注（t91）】`&&`/`||` ASCII 别名已退役：t78 降为 W-OP-RETIRED 警告态，t83 转为拒绝（E-OP-RETIRED），`Kind.LAND/LOR` 产出者随之清理。

## 二 决策：**项位** `→` 继续产 `HirTBin`（本 ADR 最重要的一条）

名字化之后，`CallExpr(名字, 实参)` 成为这些符号的**唯一 AST 形态**。项位（`term()` / `termQuiet()`）原本对 `BinExpr` 产 `HirTBin`；若按 `CallExpr` 默认产 `HirTCall`，**既有 HIR 产物会变**。

**证据（不是推测）**：队长用 `jsoncmp/old`（t74 前全量 68 样本 HIR JSON 基线）对比本轮全量重导，第一次比对即 **DIFF=1**：
```
old: HirTBin  op="→"              nid=350   ← 项位蕴含
new: HirTCall callee=HirTName("→") nid=351
```
受影响样本：`core/logic/logic.subl`（定理 `rangeLowerBound` 等）。修法：`PropNormalizer.nativeTermBinName` —— `CallExpr(原生二元名, 恰 2 实参)` ⇒ `HirTBin(name, ...)`，与旧口径一致。

> 这一条是「e2e 绿 ≠ 产物没变」的实证：e2e 只比 ok/red 与诊断码，`HirTBin→HirTCall` 它**看不见**。

> **更正（2026-11-09 12:5x，syntax 实测指出）**：本文曾断言「提示/警告不进 JSON」，**这是错的**。`HIR JSON` 的 `diagnostics` 段**包含全部诊断**（实测基线 68 样本：`hint` 3、`warn` 2、`supplement` 59、`error` 10，覆盖 26 个文件）。t74 之所以 `SAME=68`，是因为它**没有新增任何诊断**，不是因为提示不进 JSON。**新增任何 W/H/D 诊断都会改 JSON。**

## 三 决策：**值位**暂不收窄（回落 `BinExpr`）

`true ∧ false` 在 t74 前走 `BinExpr` ⇒ `HirBinExpr("∧")`（Bool 内建算符）。名字化后它成 `CallExpr`，若直接走查名会落 `E-UNBOUND-NAME`——那是**行为变更**。

本批次处置：`Elaborator` 在 `CallExpr` 分支识别「原生二元名 + 恰 2 实参 + 内建算符」⇒ **回落原 `BinExpr` 通道**，产物与原行为逐字一致。

**未决（需用户裁决 Q16）**：是否把 `∧ ∨ → ↔` 收窄为**命题专用**（值位一律用 `&&` / `||` / `<->`）。
队长推导：方案 B（值位 + 命题双身份）与用户裁决 N1（`¬p` 必须是标识符）**不自洽** ⇒ 只剩方案 A（收窄）。但收窄是**语义变更**，与词法变更不该同批落地——否则出问题分不清是谁的。

## 四 决策：`¬` **不进** `propCtors`（沿用 t70 终态）

`CallExpr("¬", [p])`（即 `¬(p)`）在命题位继续 `E-PROP-FORM`。理由引自 R3：若命题可用圆括号「调用」，`f(a,b)` 与 `f<a,b>` 的区分就塌了（得看 `f` 是谁）。
（批次 1 任务书表格曾误列 `¬ | 1 | HirPNot`，已由队长更正。）

## 五 诊断：表驱动保护 + 粘连提示

| 场景 | 诊断 | 文案要点 |
|---|---|---|
| `fun ∧[p,q]` / `var ∧` | `E-NATIVE-REDECL` | 「`∧` 是编译器内置的原生命题（2 元），不可重定义」；保护名单来自 `NativeProps.arity` |
| `p∧q`（无空格）命题位 / 值位 | `E-UNBOUND-NAME` | 「未定义的名称 `p∧q`——若想写**合取**，请在算符两侧加空格：`p ∧ q`」（R1：粘连即整体） |
| `∧<p,q,r>` | `E-ARITY` | 「原生命题 `∧` 是 2 元，实参 3 个不符（写作：`∧<p, q>`）」——写法由表内元数推出，**本身可编译**（ADR-48 §八） |

## 七 遗留与风险

1. **值位收窄未做**（Q16 待裁）：现在 `¬` 命题专用、`∧ ∨ → ↔` 仍双用 —— 不对称状态**保留在树上**，需用户裁决后单独一批收口。
2. **无优先级下的混用风险（新发现，需裁决）**：
   `fun rangeLowerBound[x,l,r]: Null <x ∈ (l..r) → x >= l>` 实际解析为
   `((x ∈ (l..r)) → x) >= l` —— **不是它看上去的意思**。
   `H-ARITH-PREC` 只覆盖 `+ - * / % ^` 混用，**不覆盖命题算符与关系算符混用**。建议增设提示级诊断（如 `H-MIXED-PROP`）。样本本身未改（改样本 = 改语义，须先裁）。
3. **`→` 与 `->` 分工**：命题位 `→`（Unicode，名字材料）与类型位 `->`（ASCII `DARROW`）互不影响，已由测试 n6 与 68 样本 JSON 比对覆盖。
4. 批次 3（`⊤ ⊥ ∀ ∃` 分类、虚拟声明化）待 Q11 / Q12。

### 更正（2026-11-09 16:4x，t85 实测）：**命题位 `∧` 不走 D-5 糖，`notes` 不变**

队长在 t85 任务书里预言「命题位 `&`→`∧` 会使约 60 个节点新增 `D-INFIX` 留痕，因此 JSON 必变」。**实测：`SAME=68 / DIFF=0`（逐字节），`D-INFIX` 新增 0 条。**

**机制**：命题位的 `∧ ∨ → ↔ ¬` 是**词法单例符号**，直接产 `BinExpr("∧")` → `PropNormalizer` → `HirPAnd`，**不经 D-5「标识符中缀」通道**，故无 `D-INFIX` 留痕。迁移前 `&` 也走同一 `BinExpr` 通道产同一个 `HirPAnd`；且 HIR 四公共字段不记算符文本、`&` 与 `∧` 等长 ⇒ **逐字节相同**。

**队长错在哪**：qa 的 t77 报告（Q3/F7）**已经写明**「`D-INFIX` 在命题位分派通道丢失、实测 notes 全空」，我随后写 ADR-49 §八 时还接受并登记了这条。**手里有证据，仍在 t85 任务书里预言 63 条**——这是"看过 ≠ 用上"。

**教训**：预言影响面时，必须**先回查已有实测结论**，不能凭机制直觉外推。
